# Scan React Native

- Read package.json, lockfiles and workspace metadata without executing JS config. Find the app entry through package.json main, expo-router/entry, AppRegistry or the app’s App component. Resolve hoisted dependencies from workspace manifests. Profile the app folder and note the workspace package manager and where its scripts run.
- Identify Expo by its runtime dependency plus app config or Expo entry. Native folders can coexist with Expo. Recognize bare apps from React Native entry and native host integration. Inspect both Android and iOS configuration and report only configured platforms. Web-only React and React Native libraries without an app entry are outside this route.
- Follow the entry, Expo Router layouts or NavigationContainer and providers. Find tokens in the project’s theme, StyleSheet files, design-system package, or NativeWind config. Record the actual state pattern (for example `hooks`, `zustand` or `redux-toolkit`) and evidence for its architecture.
- List reusable components and prop names from JS declarations or TypeScript types. Exclude route entry files and screens. Record Storybook stories only when the component has one. Determine structure from feature folders and shared components.
- Record `js-i18n` for runtime app translations such as i18next, i18n-js, Lingui or React Intl. Inspect the real message sources, locale negotiation, logical insets and I18nManager usage. A dependency on expo-localization alone does not supply message catalogs.
- Record screenshot tooling only when there is a capture path in an existing Maestro flow, Detox suite or equivalent runner. React Native Testing Library snapshots are structural evidence, not PNGs. Use the JS/TS Sauces linter for evidenced findings and review each match.
