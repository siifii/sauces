# Sauces v0.1: design

Date: 2026-11-24. Status: approved by the user 2026-11-24. This design extends `docs/superpowers/spec.md`, which stays the reference for pipeline details. Where the two disagree, this document wins.

## 1. Intent

Sauces is a **public** Claude Code plugin. Any mobile developer can hand it a design from anywhere (Figma, screenshots, a PDF, loose SVGs) and get UI that is well made for their platform. That means Android Compose, iOS SwiftUI, KMP/CMP and Flutter, each done the way that platform's community considers good practice, not one generic style translated four ways.

It has to adapt to the user:

1. **Follow.** If a project exists, follow it: its theme, components, architecture, folders and naming.
2. **Advise.** If the existing project falls short of good practice somewhere that the new UI touches, say so and offer recommendations. The user picks; nothing changes unless they choose it.
3. **Create.** If no project exists, create one with the platform's best practices by default, or with the user's stated preferences, then build the UI into it.

Because it's public, "perfect" means it holds up on strangers' repos, not just our fixtures. Concretely: a developer would merge the output without rewriting it, and Sauces is honest when it can't read, build or render something.

## 2. Goals, non-goals, anti-goals

**Goals**
- Mixed inputs: Figma links, PNG/JPG, PDF, SVG, grouped into screens and states.
- Three modes (follow, advise, create), chosen automatically from the scan and confirmed with the user.
- Per-platform best practices written down in reference files, so the same rules drive scan, plan, build and verify.
- A real render-and-diff verify loop on every platform, with a manual-checklist fallback that says plainly it's a fallback.
- A report a developer would show a client: component graph, reuse stats, fidelity scores, design audit, TODOs and best practices.
- **Localization and resources as a headline strength** (the user's emphasis):
  - Every generated string goes to the platform's resource system (ARB, String Catalog, `strings.xml`, `composeResources`), with keys named by feature and meaning.
  - Plurals and placeholders use the platform's own formats.
  - Layouts use start/end, never left/right, and directional icons mirror in RTL.
  - Icons and images become proper platform resources: vector drawables/`ImageVector`, asset catalog entries, Flutter assets with resolution variants.
  - Verify renders one RTL pass (pseudo-locale or Arabic) per screen alongside the default.
  - The report has its own "Localization & resources" section: strings added, keys reused, RTL issues found, and assets created.
- Re-running is safe: Sauces resumes from `.sauces/` state and never duplicates components.

**Non-goals (v0.1)**: web targets, backend/API wiring, writing back to Figma, animation beyond simple state transitions. Create mode makes a minimal app shell to host the UI. It is not a general app generator: no auth, networking or persistence.

**Anti-goals** (failure even if it technically works):
- The output looks or reads the same on every platform: Material on iOS, UIKit habits in SwiftUI, and so on.
- Any hard-coded color or user-facing string in generated code.
- Changing user code the user didn't approve, or silently overwriting a user component.
- Claiming something was "verified" when nothing was rendered.
- Needing heavy dependencies to install or run the plugin.

## 3. Constraints

From `CLAUDE.md` (unchanged): skills are imperative instructions for Claude; each SKILL.md body stays under ~2,000 words with platform detail in `references/`; paths use `${CLAUDE_PLUGIN_ROOT}`; all working state goes in `.sauces/` in the target project; scripts run with `python3 -I`, use only Pillow and numpy, and have `--help`; `claude plugin validate` must pass.

Environment facts that shape the build (checked on the dev machine 2026-11-24): Flutter, Xcode 26.1, Swift, Java and `pdftoppm` are installed. Gradle is not, so Android and KMP builds rely on the Gradle wrapper downloading Gradle (needs network). Homebrew `python3` has neither Pillow nor numpy, so the scripts must fail with a clear install hint when they're missing. Development uses a git-ignored `.venv`.

## 4. Approaches

**How the whole build is ordered**
- **A. Vertical slice, Flutter first.** *(Chosen; the user handed the how to Claude.)* Get one platform fully end to end in both follow/advise and create modes, then add SwiftUI, Compose and KMP/CMP through the same pipeline. Flutter goes first because golden tests render headlessly and the toolchain is present. This proves the riskiest part (verify) first and has something releasable early.
- B. Phase by phase across all platforms (the original `plan.md`). Rejected: nothing works end to end until the end, and verify problems surface late.
- C. All instructions first, tooling last. Rejected: nothing gets checked against reality for too long for a public plugin.

**What create mode produces**
- **A. Create a real project, then build into it.** *(Chosen; the user agreed to the recommendation.)* The result runs and can be visually verified.
- B. Produce only a UI kit folder. Rejected: it loses verification, which is a core selling point.

## 5. Design

### 5.1 Commands

The seven commands from spec §3 remain, plus one:

| Command | Does |
|---|---|
| `/sauces:scaffold [platform]` | **New.** Create mode: creates a best-practice project shell for the chosen platform(s) with theme slots, then hands off to the pipeline. |

`cook` decides the mode after `scan-project`:
- Scan finds a supported project → **follow**, with **advise** findings collected for the plan.
- Scan finds no supported project → offer **create**: ask which platform(s), show the best-practice defaults marked "(Recommended)", let the user override any of them, then run `scaffold`.
- Scan finds an unsupported or ambiguous project (for example, both Flutter and native iOS at the root) → ask which one to target. Never guess.
- **KMP with native UI per platform** *(Claude's call, following the "follow the project" principle)*: build UI where the project keeps it. Compose in `androidMain` or the Android app goes through the Compose rules, and the SwiftUI app goes through the SwiftUI rules. Tokens go in `commonMain` only if the project already shares them there. The v0.1 KMP fixture covers shared CMP UI only; the native-UI case is handled by the existing Compose and SwiftUI pipelines and documented in the KMP references.

### 5.2 Advise: recommendations

`scan-project` records **findings**: places where the project falls short of the platform's best practices *in areas the new UI will touch*. Examples: no central theme, hard-coded colors, strings not localized, no RTL support, components without previews, no screenshot-test tooling.

`plan` turns findings into **recommendations** in a separate section of `plan.md`/`plan.json`. Each one has an id, what was found (with file paths), why it matters, and options. The options always include "keep as is", which is the default, plus one or more concrete changes with their impact and the files they'd touch. The user chooses at the same approval gate as the plan. `build` applies only the recommendations the user chose, and logs each in the report.

Rules:
- Without a recommendation chosen, the new code still follows the project. If the project hard-codes colors, the new code still uses tokens, but it puts them where the project keeps its styling, and a recommendation offers to centralize them. The anti-goal of no hard-coded colors or strings in *generated* code always holds.
- Recommendations never touch code outside what the new UI needs unless the user picks an option that says so explicitly.
- **Strings when the project has no localization** *(Claude's call)*: follow what the platform supports without new dependencies. Use a String Catalog on iOS and `strings.xml` on Android, since both are built in. In Flutter without `flutter_localizations`, put strings in one feature-level strings class (for example, `LoginStrings`). Text kept in that one place counts as not hard-coded. A recommendation always offers proper localization (ARB + `flutter_localizations`), with its pubspec/config changes listed. The lint gate checks for string literals inside widget/view code, not inside that strings class.

### 5.3 Create: scaffolding

Each platform has a template profile. Its default choices are in the table below, each one user-overridable. Versions are the latest stable at build time; record the verification date in the reference file.

| Platform | How it's created | Default stack |
|---|---|---|
| Flutter | `flutter create` (official), then Sauces adds structure | Feature-first folders, Material 3 theme via `ThemeData` + `ThemeExtension` for custom tokens, BLoC/Cubit, `flutter_localizations` + ARB, golden tests |
| iOS SwiftUI | Sauces template: an app target plus a local Swift package for the design system and features. There's no official CLI that creates an `.xcodeproj`, so the template ships a minimal project or uses a project generator if one is installed. Choosing between those is left to the builder; record the choice. | iOS 17+, MVVM with `@Observable`, asset catalog colors, String Catalogs (`.xcstrings`), swift-snapshot-testing |
| Android Compose | Sauces template (no official CLI): Gradle wrapper, version catalog, Compose BOM | Material 3, MVVM + `StateFlow`, Hilt, `strings.xml`, Roborazzi |
| KMP/CMP | Sauces template modeled on the official KMP wizard layout | `commonMain` UI, Material 3, ViewModel from the JetBrains lifecycle libraries, `composeResources` strings, desktop target used for headless screenshots |

Templates live in `skills/scaffold/assets/<platform>/`. Scaffold never runs inside a non-empty folder without asking.

**Several platforms in one run** *(Claude's call; the user has handed over the how)*: when the user picks more than one platform (for example, native iOS and Android), scaffold creates sibling folders (`flutter/`, `ios/`, `android/`, `kmp/`) under one root. There's one shared `.sauces/` at that root. One ingest, one set of design tokens, and one plan with a section per platform go through one approval. Per-platform outputs live in `.sauces/<platform>/` (plan details, verify results), and the report has a section per platform. Each platform is built to its own best practices from the same tokens. Follow mode in a repo with several supported projects uses the same layout once the user has picked which ones to target.

### 5.4 Platform best practices

Each pipeline stage keeps its own platform references, as `plan.md` already does: `skills/scan-project/references/<platform>.md` (detection), `skills/build/references/<platform>.md` (how to write good UI on that platform), `skills/verify/references/<platform>.md` (how to render). The build references are the core "good practices" content. Each covers: token/theme mapping, component API patterns, previews, strings + RTL, accessibility (labels, touch target sizes, dynamic type/font scale), state-management wiring stubs, folder placement, and a short "don't" list. The advise findings are derived from the same build references, so recommendations and generated code never disagree.

Where an API's existence or current shape is uncertain, the reference says so rather than inventing it (CLAUDE.md rule).

### 5.4a Design-system structure (added 2026-11-24 at the user's request)

The user chooses how components are organized; Sauces recommends one from the evidence. Patterns offered:

| id | Pattern | Layers / folders (names adapted per platform conventions) | Fits |
|---|---|---|---|
| `atomic` | Atomic Design | atoms → molecules → organisms → templates → screens | designs (esp. Figma) already named that way; teams that think in atomic terms |
| `layered` | Layered design system (Material 3 / Carbon / Polaris style) | tokens → foundations → components → patterns → screens | Figma libraries with component sets + variants and tiered variables (primitive → semantic); multi-screen apps with many reused components |
| `feature-first` | Feature-first with a shared core | `core/` (theme + shared widgets) + `features/<f>/widgets` | small designs, few reused components |
| `follow` | Follow the project's existing structure | whatever scan detected | default in follow mode whenever the project has a discernible structure |

- **Signals.** `ingest` records design-system signals in the manifest: Figma page/frame/component naming (e.g. `Atoms/Button`), component sets and variant counts, variable collections and their tiers, published-library use; for images, the reusable component candidates with occurrence counts across screens and states. `scan-project` records the project's current component structure (pattern + paths + evidence).
- **Recommendation.** `plan` scores the patterns from those signals and presents the recommended one with its reasons and the alternatives, at the same approval gate as the rest of the plan. In follow mode `follow` is recommended when a structure exists; switching patterns applies to new code only, and moving existing files is a separate recommendation that defaults to "keep". In eval mode the recommendation is taken.
- **Build** places every new component in the chosen pattern's layer (the plan item records its `layer`), and **scaffold** creates the chosen structure in create mode. The **report** has a "Design system" section: chosen pattern, why, and components per layer.
- Plan items keep the universal `level` (token/atom/molecule/organism/screen) as the hierarchy; the pattern maps levels to layers and folders.

### 5.5 Figma

The ingest skill uses whichever Figma MCP tools are connected, whether the plugin's own `figma` server or a claude.ai Figma connector. It looks for tools named `get_design_context`, `get_screenshot`, `get_variable_defs` and `get_metadata` under any server prefix. If none are connected, ingest says so and suggests connecting one. It never skips the link silently. `.mcp.json` keeps the official server, and the README explains that a connected claude.ai Figma connector works too.

### 5.6 Verify per platform

| Platform | Render with | Notes |
|---|---|---|
| Flutter | Golden tests that Sauces writes under `test/sauces/` | Load real fonts; by default goldens render the Ahem test font and would score badly |
| SwiftUI | swift-snapshot-testing in an iOS Simulator via `xcodebuild test` | Fixed device size and scale to match the reference |
| Compose | Roborazzi on the JVM (Robolectric), no emulator | Needs the Gradle wrapper to download |
| CMP | Desktop target screenshot test | Fallback: Android target with Roborazzi |

If the project already has screenshot tooling, use it. Otherwise add the platform default as a test-only dependency, and only with the user's approval: it's a dependency change and goes through the plan gate. Score with `scripts/visual_diff.py` (pixel + SSIM, 0–100, default threshold 90, max 3 fix iterations). Placeholder content and system-font differences are reported, not "fixed" by hard-coding values.

### 5.7 State and resuming

`.sauces/state.json` records which stage finished, when, and against which source hashes. `cook` resumes from the first unfinished or stale stage. A changed design source invalidates ingest and everything after it. Generated files carry no markers in user code; the list of generated and changed files lives in `state.json` and the report.

### 5.8 Test fixtures and samples

- `examples/targets/`: four sample apps, as in plan Phase 1, but **buildable** wherever a toolchain is available. Flutter and SwiftUI must build here. Compose and CMP must build when the Gradle wrapper can download. Each has a small theme and 2–3 components, plus at least one deliberate best-practice gap (for example, a hard-coded color) to exercise advise.
- `examples/designs/login/`: a sample login design (default, error and loading states) that ships with the plugin, so evals don't depend on private files. The user may add real Figma/PNG/PDF exports alongside it.
- An empty target, used to test create mode.

### 5.9 Public release

The user's goal is that people install and use it as a plugin. Distribution *(Claude's call)*:
- The repo is its own marketplace: `.claude-plugin/marketplace.json` lists `sauces`, so anyone can run `/plugin marketplace add <owner>/sauces` and then `/plugin install sauces@<marketplace>`.
- After v0.1 is stable, submit it to the official plugin directory.
- The repo URL is assumed to be `github.com/siifii/sauces`, matching the current homepage. Confirm it before release.
- The privacy policy is `PRIVACY.md` in the repo, linked from `privacyPolicyUrl`. It says Sauces sends nothing anywhere itself, and Figma data flows only through the Figma MCP the user connected.

README (install, usage, the three modes, requirements, privacy note about Figma), `LICENSE` (MIT, as plugin.json declares), `CHANGELOG.md`, plugin icon (512–2048 px square PNG), `privacyPolicyUrl` (the validator expects one because of the remote Figma MCP), marketplace entry, and `scripts/eval.py` with its baseline table checked in. Also a git repo, with a commit per milestone.

### 5.10 Build order (replaces plan.md phases 1–8)

1. Foundations: git, Python dependency check in every script, JSON schemas (manifest, profile, plan with recommendations, state), fixtures, sample design.
2. Flutter end to end: scan → ingest → plan (+ recommendations) → build → verify → report → cook, in follow, advise and create modes.
3. KMP/CMP (Compose Multiplatform) through the same pipeline — moved up at the user's request (2026-11-24).
4. SwiftUI.
5. Android Compose (shares most Compose rules with step 3).
6. Eval across every fixture × sample, then public polish (5.9).

Each milestone ends with its exit check: validate passes, the eval rows for that platform pass, and the generated code shows no hard-coded colors or strings.

### 5.11 Eval *(Claude's call)*

- `scripts/eval.py` (stdlib + Pillow + numpy) has two modes:
  - **Score mode** (the default) reads existing `.sauces/` outputs in each fixture and prints the table.
  - **`--run` mode** first shells out to `claude -p --plugin-dir <plugin>` per fixture × sample. This costs tokens, needs network and its results vary between runs, which the README says.
- In `--run` mode the plan gate is satisfied by an `.sauces/eval-approve` file that eval.py writes. The plan and cook skills honor it only when the file exists, and they log that the approval was automatic. Interactive use never sees it.
- **Blocking per row:**
  - The project builds.
  - Rendering succeeded.
  - There are zero hard-coded colors or strings (per the 5.2 rule).
  - Fidelity is ≥ 90 on the **shipped sample design**. The sample uses fonts the fixtures bundle and real copy, so 90 is reachable.
- **Reported, not blocking:**
  - Fidelity on user-supplied real exports.
  - Compile-on-first-try rate.
  - Reuse precision, which a human reviews at each milestone.

Note: `privacyPolicyUrl` and the icon are plugin-directory listing checks. They print warnings but don't fail `claude plugin validate` (confirmed 2026-11-24), so they're needed only for release, not for milestone exit checks.
